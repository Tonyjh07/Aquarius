# 文档地图与分工
<!-- docs-sync: 2026-10-23 @ cb256b8 -->

> 一页说清每篇文档**写给谁、管什么、谁是权威**。改文档之前先在这里找它的位置——
> 位置不清的文档会同时变成手册、历史档案和待办清单，最后没人读完。
>
> 三条规矩：**一个事实只有一处权威**（其余地方只留一句结论 + 指向）；**用户面不出现内部编号**；
> **存档只读**，不随代码更新。

## 分工的边界

- **设计 vs 实现规格**：内核（领域模型、端口、应用层、存储、权限）留在 DESIGN；
  单个适配器的形态规格（GUI 窗口与输入栏、关系图通道分配）各自成篇，与 DESIGN 同级但只管那一个适配器。
- **设计 vs 决策**：DESIGN 回答「现在什么是真的」，decisions 回答「为什么这么定、否决了什么」。
  DESIGN 不写演化史；decisions 不重复设计结论。
- **档案 vs 规划**：做过的进 roadmap，没做的进 plan，两者不混写。
- **手册 vs 参考**：guide 讲怎么做（场景、白话），usage / configuration 讲是什么（逐条、逐字段）。

## 存档

`docs/archive/` 放**没人读但有用**的稿子：被后续决策取代、仍能解释「当时为什么这么选」的设计稿。
存档保持原样（含已经过时的结论），只在文件头标一行「已被谁取代」，**不随后续代码更新**；
外部文档也不再按名字引用存档内容。

## 维护

- 新增文档前先问：读者是谁、它管的事实有没有别处已经在管？有就先改那一处。
- 事实变了：改权威处，再按文件名搜一遍别处是否残留旧口径。
- 删一篇之前确认没有文档或代码注释按名字引用它；存档不删。
- 改了 `docs/**/*.md` 或 `README.md` 之后跑 `go run ./cmd/docsync`（见 [development.md](development.md)）。
