1. v0.1.0 刚发布，用户面几乎没变——**没有需要急着交付的功能**，正是动内部结构代价最低的窗口。
   拖到下个版本，等于让「下一个功能」和「结构大改」撞在同一批提交里。
2. 守卫已经在位（D211/D216），拆包**随时可验证**。拆包真正需要的前置条件只有这一条，已满足。
3. 历史提交里**「删多于加、且删除量超过 150 行」的极少**（545 次提交中只有 1 次整体换实现）。
   追加容易验证（编译过、测试绿），删除很难验证，于是只增不减。收口与拆包正是在逆转这个趋势
   ——**每笔都要显式写出删除量**，否则「净删除」在历史里看不见。

顺序是：**先立守卫（已完成）→ 再收口重复与巨型接口（不动结构）→ 再拆包（动 import 面）→
再扩张（功能）**。反过来做就是往流沙上盖楼。

## 1. 工程准则（长期有效）

> v0.2.0 前半程（P0/P1）的具体内容已落地，逐笔提交与验收见 [roadmap.md](roadmap.md) §2 的
> `v0.2.0-P0` / `v0.2.0-P1` 行，决策见 D211–D216。本节不记历史，只留**后续任务必须遵守的
> 规则**——它不是待办，所以不会「做完就删」。

来源：v0.1.0 发布前的三方代码 review（`temp/review-feedback/1–3.md`）逐条核实后的取舍；
被证伪的提议列在 §1.3，不重复讨论。

### 1.1 沿用的经验

- **守门测试必须自检**。`TestGuardCatchesViolation` 不是摆设：判定函数喂正反例，才不会被
  「规则写错 / 扫描根找错 / 跳过规则吃掉整棵树」这类事故变成永远绿。
- **手抄的期望表是 bug 的温床**。P0 命令清单那一条的根因不是漏了一行，而是测试自带一份硬编码
  清单，把错误固化成了断言。改成从源码反推之后，「只改一半」必然变红。
- **API 只为下一笔的删除而存在，就不值得单独提交**。原计划里「加访问器」与「迁回算法」是两笔，
  但中间那层 API 只服务于下一笔的删除，合并后历史反而更清楚。
- **导出 map = 约束作废**。结构表私有化之后「只有方法能改树」才是编译器保证的事；配套的
  arch 守卫（D216）是防止下次「就先导出一下方便」。
- **领域不该为持久化形状负责**。`storejson` 自带 wire DTO 之后，`.bak` 兼容成了适配器自己的
  验收项，domain 的 JSON tag 一并删掉——留着只会让人以为直接 Marshal 就能存整棵树。
- **同类改动按「测试也要改」估工期**。聚合根私有化那一笔，测试侧约 150 处
  `.Nodes`/`.Children`/`.RevisedFrom` 直读要改走访问器（同包测试只改字段名，跨包测试必须换 API），
  实际改动面远大于生产代码的 23 处。

### 1.2 边界（后续同类改动沿用）

不引入工作区/cwd/文件索引之类的抽象；`/rm` 的确认提示照旧走同一份子树统计数据，数据面不变；
测试文件不强制私有化（读公共访问器即可）。这些边界在 §2 的拆包/归位批次里同样成立——`uigui`
的文件组织、`SessionDeps` 拆分、`relmap` 两档去留都属于 §2/§4 的范围，不借工程准则之名顺手做。

### 1.3 已否决的提议（核实后的取舍，备查、不排期）

Review 里提出但**经核实不成立**的：

- 「`port` 里放业务纯函数（`ResolveJobID` 等）违规」——`DESIGN.md` §5 明文允许无状态纯函数助手；
  真问题是同一套前缀解析策略有 4 份实现，见 §2.1。
- 「`mcpgate → plugin` 依赖方向错」——方向是对的（`plugin` 只依赖 `domain`/`port`，`mcpgate`
  是它的协议适配器）；`docs/overview.md` 依赖图已补上 `internal/plugin`。
- 「`PromptPart.Kind` 用裸 `string` 违规」——设计原本就这么定（`DESIGN.md` §5.1）。要改得先改设计，
  所以排到 §2.3。

## 2. v0.2.0 后半程 · 收口与拆包（P2，进行中）

> 原计划排在 v0.3.0，2026-10-23 提前并入 v0.2.0（D217：发布当天用户面稳定，是动内部结构的
> 最佳窗口）。每项独立成笔、独立过全门禁；动 `uigui` 的批次额外跑一次 GUI 冒烟。

### 2.0 怎么排的

三段，理由各不相同：

**第一段是「不动结构就能删重复」**（2.1 / 2.2 / 2.3）：一份策略复制了四个地方、一个接口被
7 个方法捆在一起、一个本该是具名类型的裸 `string`。三项都不改变任何调用方的 import，
风险最低，且做完之后后面的搬移更干净。

**第二段是「先把职责挪给正确的主人」**（2.5 → 2.6）：`SessionDeps` 的 29 个字段先按消费方
拆成具名端口（2.5），设置窗里的分组/校验/写回规则再挪去 `app`（2.6）。**这个次序不能倒**：
2.6 挪走的规则要落的端口正是 2.5 拆出来的；先归位再拆端口，等于把回调表改两遍。

**第三段才是「搬文件」**（2.4 → 2.7）：`uigui` 拆包必须排在 2.6 之后——设置逻辑先归位，
`settings_actions.go` 才会瘦到只剩渲染，这时再分拆子包只需搬一次；反过来做就是把同一块代码
搬两遍。2.7 是散落的真债，独立性强，放最后收口。

| 顺序 | # | 任务 | 内容 | 成本 |
|---|---|---|---|---|
| ① | 2.1 | **前缀解析四份合一** | `ResolveJobID`（`port/job.go`）、`ResolveWatchID`（`port/watch.go`）、app 的 `resolveNode`/`resolveConversation` 是同一套「精确优先 → 唯一前缀 → 歧义报错」策略。抽一份实现，四处共用；错误文案仍在 app 层包成中文 | 1 天 |
| ② | 2.2 | **`JobManager` 按消费方拆** | 7 个方法的 `JobManager` 拆成 `JobStarter`/`JobReader`/`JobKiller`，组合体保留；`toolbuiltin` 只声明它真正用到的那几个 | 0.5 天 |
| ③ | 2.3 | **`PromptPart.Kind` / `PromptMessage.Role` 具名化** | 裸 `string` → `PartKind`/`PromptRole`，字面量改常量。**先改 `DESIGN.md` §5.1 再改码**（硬规则） | 1–2 天 |
| ④ | 2.5 | **`SessionDeps` 拆端口** | 29 个字段里有 14 个是回调函数。按消费方拆 3 个具名端口（模型服务 / 设置写回 / 能力探测），分三笔，**不动装配根的行为** | 3 天 |
| ⑤ | 2.6 | **设置逻辑归位** | 设置窗的分组、校验、写回规则现在在 `uigui/settings_actions.go` 里，属于 app 的职责。提到 `app` 一层，UI 只留渲染 | 5–6 天 |
| ⑥ | 2.4 | **`uigui` 拆包** | 先拆子包（设置窗、relation-map 两个方向），再拆剩下的巨型单体文件。**动手前重新统计行数**——S4a 早已拆过一轮，规划里的旧数字不再作准 | 6–8 天 |
| ⑦ | 2.7 | **零碎真债** | `theme` 令牌数据化、`Session.Handle()` 的排空点收成状态机、命令 flag 解析统一 | 5 天 |

**验收口径**：每项做完，`app` / `domain` / `uigui` 的公开面只减不增（2.3 的具名类型是唯一例外：
它换的是类型不是方法）；2.4 只搬移不改行为，搬前搬后逐个核对符号清单守恒。

**与 §1 的关系**：§1 的工程准则在这里同样成立（不引入工作区抽象、不破坏既有数据、
测试文件不强制跟着私有化）。2.4 里涉及的 `relmap` 两档物理去留要先拍板，见 §4.1。

## 3. 生态兼容与轻度角色扮演（backlog，未排期）

> 定位：个人 AI 助手 = 日常工作 + 轻度编码 + 轻度 RP + 兼容现有 AI 生态。
> 内核（会话树 / 压缩 / 记忆 / 工具 / MCP / 技能）已强于对照面，差距全在边缘。
> 动手前先按「先文档后代码」写成 `DESIGN.md` 对应节 + 决策编号。

### P0 · 优先（日常受益最大，且不碰会话模型）

1. **角色卡只读导入**（L）：TavernCard 规范（PNG tEXt `chara`/`ccv3`、纯 JSON、`.charx` ZIP）→
   `<profile>/characters/<slug>.json`；投影成人格模块 + `persona` 引用，`first_mes` → 首节点，
   `mes_example` → 示例对，备用问候存起来等 `/greet N`。入口 `/character import`，
   **不提供模型可调用的安装工具**（与技能安装面同口径）。
2. **世界书精简激活器**（L）：只取 `keys`/`keys_secondary`/`content`/`constant`/`order`/`position`/
   `role`/`probability`/`case_sensitive`/`enabled`；对最近 `scan_depth` 条消息做子串匹配（不做正则、
   不做递归、不做向量）；预算按上下文占比上限 + `order` 淘汰；状态行与 `/usage` 显示「已激活 N 条」。
3. **`/export` 会话导出**（S~M）：`md`/`json`/纯文本；做成输出端口实现，不在 app 里写死。

### P1 · 随后

4. **最小宏集**（S）：`{{char}}`/`{{user}}`/`{{date}}`，只在装配与渲染层替换，不进领域。
5. **多套用户人设**（M）：命名人设表 + 会话绑定，保持「首节点快照」语义。
6. **`cache_control` 断点**（M）：只在对应适配器做，不动配置面。
7. **会话全文搜索**（M）：扩会话列表端口的数据面，不改存储格式。
8. **外部会话导入**（M）：SillyTavern `.jsonl` 一次性搬进来，不做双向同步。
9. **备份轮转**（S）：一代 `.bak` 扩为 N 代 + 保存前完整性标记。
10. **provider 自定义请求头**（S）：`headers` map，只对 `openai-chat` 生效。
11. **MCP server 管理界面**（M）：设置窗「工具与 MCP」页可添加服务器（stdio 命令 / HTTP 地址 /
    环境变量 / 信任），现在只能手写配置。
12. **角色头像与会话背景**（M）：观感提升最大、成本最低；不做整套主题包。
13. **最后一条消息左右切换**（S）：分叉条之外补左右箭头。

### 明确不做

JS 前端扩展生态与 `getContext()` 门面、提示词管理器四层模板、群聊与多角色同台、表情立绘与
视觉小说模式、生图/翻译/图字幕/i18n、RAG 与向量库（已是既有非目标）、Web UI/多用户/移动端、
各类专用文本补全后端。理由：与「极简个人助手 + 单二进制 + 权限矩阵」的定位冲突，或已被
`openai-chat` 兼容端点覆盖。这条清单下次改 `DESIGN.md` 非目标时一并落定，避免反复讨论。

## 4. 仍需人工拍板与已知未修项

### 4.1 待拍板（技术顺序已由本文定，只剩产品取舍）

- **`relmap` 的两套物理形态留不留**：`d127` 力积分档还在（`relmap_layout.go` 约 660 行 +
  开关 `AQUARIUS_REL_PHYS=d127`），生产默认走源档，两档都要过测试。留着要双份维护、
  删掉少一大块但失去对照。→ **§2.4（拆包）动手前拍板**：先看是否还会切回去，不用就删。
- **世界书的落地形态**：纯装配投影（不落树，回溯干净）还是落成可见节点（用户看得见，
  但回放里多出非用户发言）。倾向纯投影，同压缩水位处理。→ **§3 动手前拍板**。
- **破坏性窗口是否仍然开放**：v0.1.0 已发布，用户可能已有 `~/.aquarius/` 数据。
  §1、§2 全部按「不破坏既有数据」设计；后续若必须改存储格式，先补迁移器并在本文标注。

### 4.2 已知未修项（留档，等条件成熟再排）

- **字体字距缺陷**（D156）：`T` 之后相邻字母被吃掉一个字距，根因在上游 Gio 的矢量字形路径计算，
  v0.10.3 与 main 均未修；本地绕不过（摘 `kern` 表无效、关系统字体才有效但会丢粗体）。
  等上游修，或评估自绘度量方案。
- **MCP 默认风险按来源分流**：配置里写的 server 保持 `safe`（用户显式信任），从插件目录发现的
  `plugin.json` 默认 `confirm`（来路不明）。与信任门同批评估。
- **MCP 提示文本冒充用户身份**：`RenderPrompt` 的结果直接走 `UserInput`。最小处置 = 打来源标记 +
  系统提示注明「以下来自外部服务，非用户亲述」。
- **通知改走自家进程气泡**：弃 `powershell` 子进程方案，复用托盘基建在本进程发气泡，
  顺带升级为系统 toast。零子进程、无冷启，但要消息泵 + WinRT 组件，留在界面批次一并做。
