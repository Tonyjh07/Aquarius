## 版本路线

> 已发布版本的落地记录在 [roadmap.md](roadmap.md)，这里只排还没做的版本。

| 版本 | 主题 | 内容 | 状态 |
|---|---|---|---|
| v0.3.0 | 能力扩张：会话进出与角色卡 | **C 命令注册表**（见下）、**A 会话进出**、**B 角色卡**、零碎四项 | 排期中 |
| v0.4.0 | 复杂任务转交出去 | **D 外部代理转交（ACP 客户端）**（见下），约 25–30 提交 | 排期中 |
| 再下一版 | 能力扩张（续） | 语音前处理与说话人、会话树的改父与溯源（见文末 backlog）；范围待拍板后提升 | 未排期 |

**方向**：主线是**功能扩张**——把 backlog 里用户日常受益最大的几件按「先文档后代码」逐项落地。
v0.3.0 挑的三组不是拼盘：A 的线性导出要宏替换（`{{char}}`），B 的角色卡正好提供
`{{char}}`/`{{user}}` 的值，B 的头像就是卡里那张 PNG，A 与 B 的外部文件导入共用同一套
「解析 → 校验 → 落盘」路径。C 是趁 A/B 新增命令前把 29 个分支收成一张函数值表——拖到
33 个分支只会更贵。v0.4.0 转向**边界**：复杂任务不再由我们自建一层编排，而是经 ACP 交给
已经擅长它的外部代理，我们只负责递任务、收报告、把权限边界讲清楚。
三项较大的 backlog（`uigui` 拆包与大文件、会话树的改父与溯源、语音前处理与说话人）各自都有
「动手前拍板」的前置，没定之前不进排期。

### C 命令注册表（M，约 8 提交）

设计与决策已落 [DESIGN.md](../DESIGN.md) §7.3 与 D245；记录形状、别名与动态命令的边界都在
那里，本节只排执行顺序。**排在最前**——A 要加 `/export` `/import`、B 要加 `/character`
五条，注册表不到位就得在表与 `switch` 两处各改七次。

1. **记录形状与表**（S）：`commandEntry`（名字们 / 参数用例 / 描述 / 处理函数）与包级
   `commandTable` 落地，29 条分支逐一搬进表；只吃参数的处理函数经适配器接上。
2. **分派收口**（S）：`execCommand` 改为「建索引 → 查表 → 未命中查动态命令 → 报未知」，
   `switch` 消失；静态优先与未知命令文案逐字不变。
3. **元数据同源**（S）：`Commands()` 与 `/help` 都读表；`CommandCatalog()` 保留为装配根
   教程对照测试的入口（行为不变）。
4. **测试改造**（S）：删掉从 `switch` 反推分支名的 AST 逻辑，改为表自检（名字无重复、
   描述非空、处理器非 nil）+ 逐条经 `Handle` 打一遍 + 别名与主名等价 + 未知命令报因。
5. **文档与注释收口**（S）：`docs/development.md` 的「新增一个斜杠命令」一段改成一步
   （表里加一行）；D212 的过渡态在 D245 里显式取代；`uigui` 侧同类仍留 backlog。

**验收**：`/help` 输出与改动前逐行一致；29 条命令逐条可经 `Handle` 分派且行为不变；
别名（`/exit`）与主名等价；未知命令与动态命令两条路径都不回归；不再存在第二处需要同步的
命令清单（`git grep` 找不到从 `switch` 反推的实现）；全门禁通过。

## v0.4.0 范围（已排期）：外部代理转交

> 设计与决策已落 [DESIGN.md](../DESIGN.md) §5.18 与 D244；协议面、端口形状、配置、
> 回填口径、上限都在那里，本节只排执行顺序。

### D 外部代理转交（L，约 25–30 提交）

一句话：**复杂任务整个交给外部 ACP 代理，我们只收回报告**。我们当客户端，不当代理；
只做 ACP v1 的六个方法，`fs/*` 与 `terminal/*` 一个都不申报。

1. **端口与类型**（S）：`port.Delegate` 拆成 `DelegateLister` / `DelegateRunner` 两个消费方
   接口（范式同 `JobManager`）；`DelegateInfo` / `DelegateSpec` / `DelegateRun` 落地；装配根
   留空实现，`/delegate list` 先报「未配置任何代理」。
2. **配置面**（S）：`delegate.agents`（`command` / `args` / `env` / `workdir` / `enabled` /
   `default`）与 `delegate.timeout_sec` 的解析、归一、上限校验；`secret:` 引用经 `port.Secrets`
   在起进程时注入。
3. **进程与握手**（M）：`adapter/acpgate` 起子进程（Windows `CREATE_NO_WINDOW`、环境剔除
   `AQUARIUS_*`、stderr 有界缓冲、进程组回收），`acp.NewClientSideConnection` 接 stdio；
   `initialize` 报 `protocolVersion: 1` + 空 `clientCapabilities`，对方只认 2 时明确报因。
   **先做到「握手成功并读回 agentInfo」**——这一步过了，后面每一步都能对着假代理验。
4. **会话与提示**（M）：`session/new`（绝对路径 `cwd`、空 `mcpServers`）与 `session/prompt`
   （单条 `text` 块）；把 `stopReason` 五值映射成摘要行。`Session` 非空时报「本版不支持复用」。
5. **过程收口与回填**（M）：`session/update` 的 `Client` 实现——数工具调用（`tool_call`）、
   去重改动文件（`tool_call_update` 的路径）、攒 `agent_message_chunk` 正文；`delegate` 工具
   回填「报告 + 摘要行」，正文与改动文件按上限保头尾/只报总数。
6. **权限回落**（M）：`session/request_permission` → `port.Confirmer`；允许/拒绝映射到
   `allow_once` / `reject_once` 一类的选项（没有对应项时取第一个同类）；用户填的拒绝理由只进
   提示与审计；无人值守下当场拒绝。
7. **取消与总闸**（M）：ESC / 停止键 → 通知 `session/cancel` → 等 `cancelled`（正常终止，
   保留已交付正文）→ 宽限 2 秒后杀进程组；`delegate.timeout_sec` 总闸；每会话单路转交。
8. **发现与命令面**（S）：启动时 `PATH` 探测（只判可执行，不握手——不拿用户时间换清单）、
   `Available` 与不可用原因；`/delegate list` 接入 `commandCatalog` 与 `execCommand`（若 C
   已落地则一条记录即可）；工具描述里列出可用代理清单（零可用时不注册工具，装配时也不出现）。
9. **GUI**（M）：设置窗「外部代理」页（列表 / 可用性 / 缺省选择 / 命令行编辑）；`delegate`
   执行时转写区出**一行状态**（「已交给 <代理>，进行中…」→ 结束后换成摘要行），过程不铺开。
10. **端到端验收**（S）：假 ACP 代理跑通「转交 → 拿报告」；再用一个真代理手工验一次
    （记进发布说明，**不进自动化测试**——那要求本机装东西，违反测试自足）。

**验收**：假代理覆盖六个方法与全部错误路径（握手拒绝、崩溃、超时、取消、权限两态、非空
`Session`）；`cwd` 为绝对路径且 `mcpServers` 为空；转交后树里只多一个工具分片；确认句写明
「该代理有它自己的文件与命令访问」；无人值守下转交被拒且轮次不阻塞；零可用代理时工具不注册、
命令给出配置指引；全门禁通过（`go test -race`、`gofmt`、`go vet`）。

**风险**：

- **SDK 是 v0.x**：`coder/acp-go-sdk` 加约九千行生成类型，协议一改就跟。缓解：只经端口暴露
  三个简单结构体，适配器内部随 SDK 变；升级时对着假代理逐条回归。
- **对方的工具循环不可控**：它能跑很久、能改很多文件。缓解：总闸 + 单路 + Confirm + 摘要行
  如实交代停止原因（`refusal` / `max_tokens` / `max_turn_requests` 都要被用户看见，不能只报
  「完成了」）。
- **生态在动**：registry 里的命令名与启动参数会变。缓解：不内置预设，配置就是唯一事实源。

**明确不做**：内置代理预设、按 registry 自动安装与升级、ACP v2、客户端 `fs`/`terminal`/
`elicitation`、把子代理转录塞进树、转发我们的 MCP server、跨会话复用子代理、多路并行转交。

## `uigui` 拆包与大文件（backlog，未排期）

> 拆成三个子包（`uikit`/`settings`/`relmap`）的收益与代价已经量过：**买不到什么**，所以现在不做。
> **重启前重新统计**，下面的数字是 2026-10-25 的实测，不是估算。完整取舍与否决项见 D234。

**当时的规模**：`uigui` 152 个 `.go`、48,219 行（生产 77 文件 26,692 行、测试 75 文件 21,527 行）。
三个候选子包合计 33 文件 11,448 行 = 24%：`uikit` 4 文件 794 行、`settings`（含 `prompt_editor.go`）
21 文件 7,419 行、`relmap` 8 文件 3,235 行。搬完父包剩 44 文件 15,244 行，最大单文件从
`settings.go` 1,067 行变成 `welcome.go` 1,044 行——**「单文件太大」一条都没解决**。

**四项实测代价**（逐条都推翻了原规划里的估算）：

| 项 | 数字 |
|---|---|
| 主题令牌要导出 | `palette` 26 字段 + `paperPalette` 24 字段跨包必须首字母大写，需按类型改 **391 处**字段访问（46 个文件）；另有 340 处 `.text`/`.sel`/`.card` 属于父包别的结构体，不能机械替换 |
| 测试全是白盒 | 75 个测试文件全部 `package uigui`；子包测试依赖父包夹具（`settings` 侧 `newHeadless` 74 处、`fillSnapshot` 21 处、`testTheme` 19 处；`relmap` 侧 `relGraphFixture` 30 处、`newHistUI` 16 处、`histFrameFor` 13 处），而 Go 禁止「本包测试 → 子包 → 本包」成环；改外部测试包则要导出几十个非导出符号 |
| 装配根要改限定名 | `cmd/aquarius` 42 个名字 / 323 处引用，其中 29 个名字 / 261 处属三子包（生产 90、测试 171） |
| 反向耦合本来就少 | `uikit` 出向只有 1 个符号（`trimRunes` 1 处）、入向 27 符号 / 243 处；`relmap` 双向各 12 符号；`settings` 出向 8 符号 / 89 处。**真正的坏耦合只有两处**：`theme_paper.go` 调 `trimRunes`、`welcome.go` 摸 settings 内部符号 |

**重启判据**：出现第二个前端或第二个主题消费者；或 `settings` 的增长让 `Host` 接口反而不如

## 会话树的改父与溯源（backlog，未排期）

> 「历史管理窗编辑器化、拖节点改父」是明确要做的未来功能。这条线是三件事叠在一起：
> **改父（Reparent）**、**溯源路牌（Detached）**、**版本链（`revisedFrom`）**。三者的落地顺序
> 与直觉相反：版本链要先补洞，改父才有可靠地基；溯源路牌反过来可以独立先做。
> 任何一项动手前，先写成 `DESIGN.md` §4.1 的对应段落 + 决策记录。

### 现状事实（照代码核过，别凭印象排）

- 领域层**没有任何改父路径**：`Append` 的父恒为 Head，`Revise` 的父恒为原父（同级），
  `InsertCommitted` 只把**目标的**父改成衬垫，`Prune` 只删。把既存节点从一个父挪到另一个父，
  现在做不到。
- 关系图里「拖节点」只是**布局自由度**（自由摆放的槽位，关窗即作废、不落盘、不进领域）。
  「拖着靠近另一个父松手就改父」连雏形都不存在——不要把它误当成已有的一半功能。
- 版本链的三个洞：`Prune` 删旧版本时会连带删掉新版本的溯源记录（活节点丢溯源，图上版本虚线
  退化成顺接实线；删除前的提示已落地）；`Validate` 只查版本链两端在树，不查成环；`KeepMode`
  （另起/转移/复制）不落盘，故图上三者同一种线型。
- `Validate` 对结构边查五项（重复边、悬空父、双向一致、成环、Head 在树），对版本链只查两项。
- **版本组已不再等价于「同父孩子」**：插入摘要造出的衬垫是透明的，版本组的分组键是「最近的非
  衬垫祖先」。所以下面讨论「版本 vs 结构归属」时别把两者当同一个东西——它们现在已经有分歧点。

### 落地顺序

1. **补齐版本链**（小）：`Validate` 给版本链加**成环检查**（当前原语造不出环——`Revise` 的
   新节点 ID 全新——改父落地后才有洞）。`Prune` 连带删溯源已经是既定取舍，且删除前的提示
   已落地（确认句讲明「另有 N 个新版本会一并失去溯源记录」）；这一步只剩成环检查。
2. **溯源路牌**（中，纯增量，可与 4 并行）：Carry 之后旧节点成为无子叶，后续内容去了新版本，
   现在从旧节点一侧查不到。加一张私有表记「子树被转移到哪个节点」，只服务「点开旧版本能看它
   下面曾挂过什么」、审计与将来的撤销——**不参与**路径、版本组、装配、删除统计的任何一项。
   边界一旦松动就成了多父图（已否决的那个方向）；要「从断点挂回来」，那是**两次改父**
   （先挪回来、再删路牌），不是第二父。
   - **为什么必须存显式记录**：指向的「新版本」理论上能从版本链反查（`revisedFrom[新] = 旧`），
     但同一旧节点可以被转移两次（一对多），反查不唯一。记录里带上发生时刻与来源种类
     （转移 / 改父），顺带补上「另起 / 转移 / 复制三种编辑方式不落库、图上同一种虚线」这一档。
   - **校验要在结构边之外**：路牌天然违反「父子的双向一致」（旧节点此刻无子，而它曾经的孩子
     挂在别处），所以不能进结构边检查，只能照版本链的先例查**两端在树**；另需一条版本链没有的
     **陈旧性检查**——被记的子树根现在必须确实挂在记录指向的新版本下，否则路牌已失效
     （转移之后再改父就会这样）。
   - **落盘只走一个出口**：领域结构 → `Snapshot` → `storejson` 的 wire 格式，新键缺省即空，
     旧文件天然兼容（不需要迁移器）。展示面若要在图上标「这个旧版本下面曾挂过内容」，再给
     整树快照的节点加一个布尔位；**端口只加事实，不加语义**。
   - **随机测试**补一条断言：做过一次转移之后，必有一条路牌且指向正确。
3. **抽出 `transferChildren`**（极小，纯重构）：Carry 里那段整批边转移的内联代码收成私有方法，
   Carry 与改父共用。先重构、后加功能，改父那笔才只看新判断。
4. **改父原语**（中）：`Reparent(id, newParent)`——存在性 → 环拦截（不能挪到自己或自己的后代下，
   「严格后代」判定已有现成实现）→ 摘边/挂边/改 `Parent` → 不动 Head（Head 在子树内随行、在外
   不受影响）→ 自检。唯一真正新增的判断是环拦截；摘边挂边那几行与转移编辑里的整批边转移同构，
   这也是第 3 项先抽方法的原因。**额外要求**：改父可能让装配水位悄悄变化（把节点从有摘要的
   分支挪到没有摘要的分支，上下文会从几条暴涨回几十条），树合法、不报错——必须前后比对水位，
   变了就发一条提示，做到「可感知」而不是「不静默」。同类连带影响（估算计数跳变、压缩统计
   漂移）可接受，但同样要能被察觉。**Head 反而是安全的**：它在被挪的子树内就随行、在外就完全
   不受影响，两种情形都不需要动它（比「转移历史」简单——那个要先判 Head 是否在子树内）。
5. **命令面与拖拽接线**（大）：`/reparent` 一类的命令 + 关系图拖拽落点判定。必须排在第 4 项
   与下面「拖拽仲裁」拍板之后。

### 动手前要拍板

- **版本链与结构边跨父之后算不算数**：版本关系原本靠一个没写明的假设撑着——「版本一定造在
  同一个父之下」。改父会打破它：A′ 挪到别的父之后，它与 A 不再是结构上的兄弟，但版本链仍记
  「A′ 修订自 A」。四个选项：
  ① **禁止改父带版本链的节点**（语义最干净，但人格、摘要这类节点几乎全被锁死，功能残废）；
  ② **改父时清版本链**（视角一致，但丢溯源——删除时已经是这个方向）；
  ③ **版本组改按版本链算**（两视角合并，但推翻「版本组 = 结构兄弟」的定义，版本编号全要重算）；
  ④ **允许并存，图上画两种线**（不动数据结构，但同一对节点可能同时是「版本」与「不同父」，
  现有线型表达不了，要加一档）。
  **倾向 ④**：这里语义确实有两种（版本关系 + 结构归属），压成一种必然丢信息；这与「不为摘要
  另开一个角色」的取舍不冲突——那里多一档只增分支成本、没有新语义。**这项先定**，版本组、
  溯源查询、边型三处都顺着它走；先写改父再回头改会很疼。
- **溯源的粒度**：只记「子树去了哪个新版本」，还是也记「被搬走的那个子树根」？后者多一个字段、
  多一条陈旧性检查（指向的节点是否还挂在那里），但用户点开旧版本时能直接看到被搬走的第一条。
- **拖拽仲裁**：现在「拖节点 = 摆位置」。改父落地后同一个手势有两种含义，需要一条区分规则
  （松手位置在原父邻域内算摆放、靠近另一节点算改父，或加修饰键）。**这条不写清，接线时必然返工。**

## 语音前处理与说话人（backlog，未排期）

> 三项同属「能力扩张」，排在 backlog 的中后段。共同前提是一件事：
> 现在的语音链路是**整段式**——`port.Recorder.Record` 一次返回完整 WAV，`micwin` 单缓冲采集、
> 默认 60 秒、硬顶 4 分钟（`maxRecordBytes`），`ingestmic.Listen` 拿整段去转写。只要还在这个形状里，
> VAD 无处落脚（它要的是逐帧判定），唤醒词与声纹也没有连续的输入可喂。
> 所以次序是 **VAD 先做**：它顺手把采集口改成流式分帧，后两项才有前置条件。

### VAD（语音活动检测）：先做，S~M

**做法**：不自己写。`github.com/vithnilica/go-silerovad` 是 Silero VAD v6.2.1 的纯 Go 实现
（MIT，权重内嵌约 1.2MB）——无 cgo、无 onnxruntime、无外部模型文件，只依赖标准库，完全符合
单二进制口径。`Stream` 接受 8–192kHz 任意采样率并自带多相重采样；32ms 一块的推理约 0.95ms
（单核约 3%），实时无压力。分段默认值沿用上游：阈值 0.5、负阈值低 0.15、`MinSilence` 100ms、
`SpeechPad` 30ms、`MinSpeech` 250ms。备选 `zserge/govad`（v5 半精度、只吃 16kHz、低维护）
仅作兜底，不选。

**前置改动（这条是主要工作量）**：`port.Recorder` 从「一次返回整段 WAV」改成流式产出帧，
`micwin` 由单缓冲改为连续缓冲 + 定长 32ms 读出，`ingestmic.Listen` 由「录完 → 入库 → 转写」变成
「边录边判：检到语音开始才缓冲，静音超过 `MinSilence` 就切段，逐段入库转写」。断句结果仍是
独立的 WAV 片段，附件与转写链路不动。改动涉及端口定义，**先改 `DESIGN.md` §5.6 再改码**。

**验收**：对着麦克风说三句、中间各停 1 秒，得到三段独立转写而不是一整条；
纯静音 30 秒不产生任何附件、不发起转写；`/mic` 与 GUI 语音键行为一致；端口改动的契约测试覆盖
「用户主动停止时已录到的音频照常返回」（现行语义，不能丢）。

**风险**：`Detector`/`Stream`/`Segmenter` 都非并发安全，必须一个采集流一个实例（权重只读共享，
约 1.2MB）；要求 Go 1.26+（本机满足）但**没有任何版本 tag**，只能依赖伪版本，升级得盯 commit；
仓库目前 2 个提交、0 star，属于「写得好但没人用」的新项目，接进来要把它当自有代码对待，
别指望上游及时修。模型来自 Silero VAD v6.2.1（MIT），作者请求在使用处标注引用，一并写进
`THIRD-PARTY-NOTICES.md`。

### 唤醒词：待定，暂不排版本

**现状是两条路都不通**，原因不在代码而在分发许可与运行时：

1. **openWakeWord** 代码 Apache-2.0，但**预训练模型是 CC BY-NC-SA 4.0**（非商业 + 传染），
   不能随二进制分发，也不能让用户「下载即用」地替我们绕过。
2. **microWakeWord**（OHF-Voice）代码与 `esphome/micro-wake-word-models` 都是 Apache-2.0，
   模型层面干净，但它要 TFLite Micro 的 INT8 运行时；Go 侧只找到 cgo 的 `mattn/go-tflite`，
   没有纯 Go 的 INT8 TFLite 解释器。为唤醒词开 cgo 会破坏「无 cgo、单二进制」的交付口径。

**两条未解路径**（要先拍板走哪条，拍完再进本文排期）：

- **自训 Apache-2.0 模型**：用开放语料训 microWakeWord 形状的 INT8 模型，许可证由我们决定；
  代价是要补一个纯 Go 的 INT8 推理内核（只覆盖该模型用到的算子），属于「为一项功能写一个引擎」。
- **外置 openWakeWord 服务**：不进程内跑，唤醒词交给用户自己起的服务，内核只做 HTTP 客户端。
  与下文声纹同一形状，代价是「单二进制开箱可用」降级为「要另起一个服务」。

不进入任何版本的边界，也不列验收——**先定路径**。

### 声纹识别：外置服务 + 协议位，M

**模型选型**：3D-Speaker 的 CAM++（`speech_campplus_sv_zh_en_16k-common_advanced`，代码
Apache-2.0），80 维 fbank 输入、192 维 embedding，ONNX 体积 fp32 27MB / fp16 14MB / int8 8.2MB，
中文场景可用。WeSpeaker 代码同为 Apache-2.0，但 resnet34-voxceleb 等**权重**是 CC-BY-4.0，
若走 WeSpeaker 必须逐模型核对许可证。

**为什么不进程内跑**：三个纯 Go ONNX 引擎都不够格当生产依赖——`Kazuhito00/onnx-purego-interpreter`
自述比 ONNX Runtime 慢 5–30 倍且「不作为 ORT 替代」，`AdvancedClimateSystems/gonnx` 只到 opset 13
且 2024 年后未发版，`oramasearch/onnx-go` 走 Gorgonia、自述实验性；`shota3506/onnxruntime-purego`
虽免 cgo 但通过 purego 调原生共享库，仍需分发 `.so`/`.dll`。所以**结论是外置服务 + HTTP 适配器**，
不在进程里塞引擎。

**形状**：照既有语音端口的做法办——调用方（`app`）定义一个小端口（如「音频 → 说话人标签」），
配置面按**协议位**新增一个 kind（如 `audio.speaker.kind`，`campplus` / `http` 两档），适配器把 WAV
发给服务、换回 embedding 或「是否本人」的判定。配置取值仍沿用 `base_url` / `api_key` 显式字段优先、
缺的才借 `model.providers` 的既有顺序（D222）；分派仍是白名单 + 越界即报错（D223）。

## 仍需人工拍板与已知未修项

### 待拍板（技术顺序已由本文定，只剩产品取舍）

  但回放里多出非用户发言）。倾向纯投影，同压缩水位处理。→ **世界书那条动手前拍板**
  （不在 v0.3.0 范围内，拍板后才考虑是否并入）。
- **唤醒词走哪条路**：两条都通不了现在这条道——开放模型的预训练权重不许随二进制分发，
  许可证干净的模型又缺纯 Go 的 INT8 运行时。要么自训模型并配套写一个极小的推理内核，
  要么做成外置服务（「开箱即用」降级为「另起一个服务」）。→ **唤醒词动手前拍板**，
  两条路径见上文「语音前处理与说话人」。
- **声纹识别的用途**：说话人分离（多段转写标注谁说的）与入口门（只认我的声音）是两种验收，
  先定要哪个再写代码。
- **破坏性窗口是否仍然开放**：应用已公开发布，用户可能已有 `~/.aquarius/` 数据。
  本文所有任务按「不破坏既有数据」设计；后续若必须改存储格式，先补迁移器并在本文标注。

  v0.10.3 与 main 均未修；本地绕不过（摘 `kern` 表无效、关系统字体才有效但会丢粗体）。
  等上游修，或评估自绘度量方案。

  系统提示注明「以下来自外部服务，非用户亲述」。
- **通知改走自家进程气泡**：弃 `powershell` 子进程方案，复用托盘基建在本进程发气泡，
  顺带升级为系统 toast。零子进程、无冷启，但要消息泵 + WinRT 组件，留在界面批次一并做。
