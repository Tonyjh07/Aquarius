## 记录

### D1 — 节点不可变；用户"改"= 创建同级新节点

- **决策**：节点不可变；用户"改"= 创建同级新节点
- **否决**：就地可变消息（v2 曾选）——放弃，换取崩溃安全与分支对比
- **状态**：生效

### D2 — Revise `Carry` = 边转移

- **决策**：Revise `Carry` = **边转移**
- **否决**：深拷贝子树（数据翻倍、身份分裂）；DAG 共享（复杂度不值）——深拷贝子树后被 D96 立为**并列第三模式**（显式选用，非默认），否决仅对"以拷贝替代 Carry"继续成立
- **状态**：生效（部分被 D96 修订）

### D3 — 流式中间态不进领域，Turn 结束一次性 Commit

- **决策**：流式中间态不进领域，Turn 结束一次性 Commit
- **否决**：节点随流变异（半节点/部分写入问题）
- **状态**：生效

### D4 — Tier-2 插件协议 = MCP（mcpgate 适配）

- **决策**：Tier-2 插件协议 = **MCP**（mcpgate 适配）

### D56 — 转写区滚动手势 = 按垂直轴夹取 + 边界由当帧钳制负责（D44/§15.1/§15.3 滚动行为落地）

- **动机/实测**：转写区的**手工滚动从未生效**（滚轮完全无反应，只靠流式尾随自动贴底）。根因（Gio 源码实证）：`gesture.Scroll.Update(..., scrollx, scrolly)` 两参分别喂 `ScrollX/ScrollY` 两路累计器，而垂直手势累加的是 `e.Scroll.Y`；`updateScroll` 却把可滚范围当 `scrollx` 传了进去 → Y 侧过滤器是零范围 → 每格滚轮都被夹成 0（Gio 自家 `layout/list.go` 就是按轴向把 bounds 换到 Y 的，`Axis==Vertical` 时喂 `scrolly`）
- **决策**：**① 范围按轴向绑定**——横向 `pointer.ScrollRange{}`（X 夹到 0，不横滚），纵向 `pointer.ScrollRange{Min: -overflow, Max: overflow}`（`overflow = total - viewH`，含 fling 溢出余量）；**② 过滤器范围不随 `scrollPx` 走**——过滤器是**上一帧**登记、事件到来时才用于夹取，随位置走会滞后一帧：边界处反向的首格被旧边界误夹成 0 丢失（下滚回去的第一格被吃）；边界反正由 `updateScroll` **当帧钳制**负责（含 fling 溢出），过滤器只求够宽——单格增量不可能超过 `overflow`。语义：`d>0` = 向新内容，**尾随贴底**（流式新消息恒贴底；上滚离底停跟随，滚回 `overflow` 恢复）；内容矮于视口时贴底锚定、`overflow=0` 不滚。无窗口测试经 `input.Router.Queue` 注入滚轮事件覆盖三态（上滚停尾随 / 下滚半程不恢复 / 回底恢复），手势区与事件投递走真实 hit 树 + 过滤器
- **否决**：把边界交给 `ScrollRange` 钳（滞后一帧误夹反向首格，与当帧钳制重复）；手势改走 pointer.Drag 翻页滚动（手感生硬，与气泡区"只滚不拖"的定位冲突）；把夹取范围直接依赖 `scrollPx`（即上述滞后缺陷的形态）
- **状态**：生效

### D70 — 元素羽化带宽统一 = 输入胶囊带宽（修订 D47/D48 按元素短边口径，§15.1）

- **动机/实测**：用户实测同屏「消息气泡边缘与输入胶囊边缘羽化不一致」。根因：D47/D48 带宽按**元素自身短边 × featherRatio** 取值——输入胶囊（48dp 短边）≈1.44dp、单行气泡（~34dp）≈1dp、多行气泡（≥100dp）封顶 3dp、chip（20dp）≈0.6dp，取整后逐 DPI 各不相同（1× 时胶囊 1px、高气泡 3px），同屏各元素边缘剖面软硬不一（合成复现：同深度像素 9 vs 27）。
- **决策**：`featherWidth` 全元素改取**输入胶囊的带宽**：`fw = clamp(round(Dp(inputRowDp) × featherRatio), Dp(featherMinDp), Dp(featherMaxDp))` 且 ≤ 元素短边 1/3（极小元素防被整带吃掉）——胶囊自身取值与改前逐位相同（其短边即 48dp），其余元素向其看齐；ratio/上下限参数、Dp 换算（DPI 响应）与 `AQUARIUS_NO_FEATHER` A/B 开关不变。只改带宽，不动圆角/剖面/SDF/落笔范围。

- **后果/限制**：① 各元素带宽收敛为胶囊值（取整随 DPI 同进退：1×=1px、1.5×=2px、2×=3px；1× 时 1px 带宽的剖面退化为内容 AA——与胶囊同款）；② 极小元素（短边 < 3×带宽）仍按短边 1/3 收窄；③ 命中语义不变（边带 alpha>0 可命中，各元素等宽）。
- **状态**：生效

- **动机**：D54 输入栏动画把胶囊/右钮各自从 logo 矩形按单标量 `barP` 线性插值到终位——三段几何同涨同缩，间隙 = p×12dp 在运动中被按比例挤压（胶囊半宽时已贴向 logo、右钮提前滑动），「胶囊与两圆的间距」不保；且缩/长与平/合混在一个进度里，「先缩输入框、再合球」的分段语义既看不出来、也不可测。
- **决策**：**状态机、曲线、时长全不动**——`barP` 本来就等于 send 的行程进度，以它为几何时钟，只把几何导出改成分段纯函数（`rowRectsFromSend`，按分界点 split = send.Min 抵达胶囊成圆处 ≈120/528 分两支）：① **缩/长段**（sendP ≥ split）：胶囊左缘钉 `pillEnd.Min`（与 logo 间隙恒 12dp），右缘 = `send.Min − 12`（与 send 间隙恒 12dp）——**send 全程同步移动**（收起 544→136、展开反向）；② **平移/合球段**（sendP < split）：胶囊已成 ⌀48 圆（宽 = 行高、停 `pillEnd.Min`），与 send 同步插值、**同时抵达** logo 合球（展开反向 = 圆先弹出到 split 再长宽）。单函数无方向参数 → 两方向同一路径，split 处连续、中途反向天然不跳变。时间线由原曲线**导出**（拍板接受瞬发段）：收起缩圆 ≈0–188ms + 合球 ≈32ms，展开分开 ≈15ms + 生长至 260ms（≈118ms 满宽、≈182ms 过冲峰）——**回弹自然落在生长段**，过冲期双间隙仍恒 12；夹取顺序改为**先 `clampRowX(send)` 再由夹后 send 导出胶囊右缘**，贴边夹掉后双间隙仍恒 12。
- **否决**：维持单标量插值（间隙按 p 挤压、分段语义不可测）；独立分段进度 + 各段重定时长（背离「send 速度按 D54 原方案不变」的拍板，状态机/反向续跑全要重做）；单侧锚定（左锚/右锚/中心缩只保一侧间隙，另一侧乱开或几何折返——拍板为双侧锚定 + send 同步）；给平移段设 ≥60ms 可见下限（send 须在段边界重映射、曲线偏离 D54）；回弹给平移段（观感落在圆钮而非输入框上）。

### D77 — 展开完成后胶囊内容淡入、收起淡出与消息区收起同刻结束（§15.1，补 D54/D76）

### D78 — 启动防闪：挂接即隐藏、首帧 ULW 提交后激活揭示（§15.1，补 D62）

- **动机**：启动闪现「未定制窗口」（roadmap Q8/1d 实测）。D62 以「分层窗首次 ULW 前不显示」兜启动白闪——该语义只在**建窗时**就带 `WS_EX_LAYERED` 才成立；实际时序是 Gio `Configure(options)` 先 `ShowWindow`、之后才投 `Win32ViewEvent`（我方 `onHWND` 才挂样式），后挂样式的间隙与首帧位图就绪前的窗口以未定制形态闪现；显隐时机「依赖平台语义」也不可测不可控。
- **决策**：改**显式状态机**（`UI.revealPending`，事件循环写、托盘线程读，atomic）：① **隐藏起点 = `onHWND`（最早可接管点）**——`Win32ViewEvent` 到达即在窗口线程 `SW_HIDE`、置 `revealPending`；`WS_EX_LAYERED`（D62，ULW 必需）保留作双保险。② **合成/提交门**——`fadeCompose` 的「主窗隐藏不提交」门改 `presentable() = mainVisible() || revealPending`：启动隐藏是我方所为，须照常合成提交（否则永不首帧）。③ **揭示 = 首帧 ULW 提交成功**——`fadePresent` 里 `presentMain` 成功 → `revealPending.Swap(false)` → `revealMain`（平台件：`ShowWindow` + `SetForegroundWindow` **激活前台**，与现状启动聚焦一致，拍板）→ 首个可见帧即带内容。④ **呼出门（拍板）**——首帧就绪前托盘/快捷键呼出**不 ShowWindow**，只投展开消息（置展开/焦点态，窗口由首帧自现）；首帧后回到既有 `hideMain/showMain` 语义（揭示一次性 `Swap`）。⑤ **协调与降级（拍板）**——置顶断言、位置/停靠恢复全在隐藏期完成（揭示即在记忆位、无跳动）；GPU 离屏失败永不首帧 → **保持隐藏**（与 D62 降级「无可显示像素」同源，托盘在、可经菜单退出）。
- **否决**：维持 D62「分层窗天然不显示」不作显式隐藏（实测仍闪，语义依赖挂样式时机，不可测不可控）；只把揭示拖到首帧而挂接时不隐藏（闪窗持续到首帧才消失，问题未解决）；首帧揭示 `SW_SHOWNOACTIVATE` 后台出现（现状启动即聚焦，改变交互预期——拍板激活前台）；首帧前呼出立即显示（位图未提交 → 闪现未定制窗口，与本项目标相悖）；GPU 降级兜底显示（分层窗无位图多半黑窗，拍板保持隐藏）；钩 Gio `Configure` / WH_CBT 拦 `ShowWindow`（需 DLL 注入且创建线程未知，复杂度不成比例）。
- **后果/限制**：① `onHWND` 之前 `Configure(ShowWindow)` → 挂钩的亚帧间隙仍可能露一帧（Gio 无首帧前挂钩点，接受）；② 启动期 `IsWindowVisible`=假 → 托盘 toggle/快捷键判「未显示」走 `showMain` → 被揭示门拦下（= 拍板行为）；③ 降级场景应用不可见（进程/托盘在，可经菜单退出）；④ 次窗不属本项（常规渲染、内容即显，无未定制闪现问题）。
- **状态**：生效

### D79 — 转写区底部常驻矮带 + 等高尾部留白（§15.3，Q13/1h）

- **动机**：转写区只有顶带（§15.3），**底缘被视口下沿硬切**——上滚离底时最下面一行被齐刷刷切断，观感生硬；D74 只解决顶带困行。Q13 已定语义（常驻视口底缘矮带 + 等高底部留白、贴底时末行在带外），带高留到实现时定。
- **决策**：① **底带常驻转写区底缘** `[transH − Dp(fadeBandBottomDp), transH)`（窗口坐标；`fadeBandBottomDp = 12`，顶带 56dp 的 ~21%，取「几～十几 dp」薄带口径）——`fadeFrame` 由单带泛化为 `fadeBands{top, bottom, lowTop, lowEnd}`：顶带原式不动，底带在带内把 `g(y)` **乘上 1 → 0 的 smoothstep**（带底 = 转写区底，末像素≈0），**带下恢复 g=1**（状态行/输入栏在带外、不受淡化）。② **滚动内容尾部垫等高空白**（`total += lowPad`，随内容滚，D74 同款）——尾随贴底/短内容贴底时**末行底 = 视口底 − 带高**，正好落在带外（D56 底部锚定、尾随语义不变，只整体上移一个带高）；上滚离底（`scrollPx=0`）时内容延伸过带 → 底缘渐隐而非硬切。③ 只在展开布局路径设带；收起态无转写区 → 底带关（`bandLowTop == bandLowEnd == size.Y`）。④ D54 揭示动画期间底带照常驻留：内容静止、末行本在带外，与顶带重叠段只是相乘，无观感问题。
- **否决**：底带与顶带同高（56dp 常驻底缘渐隐 + 尾部留白过厚，与 Q13「少量/矮」不符）；**视口固定留白**（D74 同款否决：渐隐作用于空白而失效）；梯度拉到窗口底（连状态行/输入栏一起淡掉，控件不可读）；只加留白不加带（底缘仍硬切）。
- **后果/限制**：① `fadeFrame` 签名改带结构（`lowEnd <= lowTop` = 无底带，零值即关），既有调用点同步；② `contentH`/`overflow` 含 `lowPad`（D74 同款），既有滚动断言末行底 `h → h−lowPad`；③ 梯度在 `transH` 收零后其下回 1 是断点，但转写形状裁剪上沿即带底、状态行/输入栏形状自带底起，**无同形状跨越** → 无缝；④ `transH` 低于带高的极矮窗退化为整片转写区渐隐（尺寸约束归 S1b 响应式迁移处理）；⑤ 带内半透明行按位图 alpha 命中，可滚可选（顶带同口径，D71 钉点不改）；⑥ **作用域按 clip 界定（实现后实测修正）**：底带只乘在 `clip 底 ≤ 带底` 的形状上 = 转写视口登记的滚动内容；chrome 形状（悬浮 tips `hoverTip`、状态行、输入栏——均整窗 clip，tips 几何上跨进带内）保持 g=1，否则 tips 卡片顶沿半透明（实测 bug）。顶带仍全帧生效，无此问题（chrome 不及窗顶）。
- **状态**：生效

### D80 — `port.TreeView` 会话树只读视图 + app 原子发布不可变快照（前置 A，§7.5）

- **动机**：roadmap S1-1f（消息分叉切换按钮）与 S3（会话树界面）都要读**树事实**（某节点的同级集合与自身下标），而 Presenter 只发渲染块、不给树；UI 跑在独立 goroutine，直读 `Session.Current()` 与装配根的树变更并发（`-race` 必红），铁律 5 又不许 UI 直连 store。roadmap 把前置 A 的形态明确留到「设计」这一步。

### D83 — 100% 缩放下 logo 被裁 + 羽化消失：图标随球径预缩放、渐隐跨度回归 fw+0.5（§15.1）

- **动机（用户实测）**：100% 缩放（PxPerDp=1）下两处观感损坏——① 悬浮球 logo 边缘被截，看着像被放大裁切；② 元素边缘羽化完全消失（硬切）。
- **定位**：① **logo**：`logoIconPx = 60` 是**写死的像素值**，名义取 125% 缩放的球径（48dp×1.25 = 60px，D49 行高 48），绘制按 1:1 平移。100% 下球径 = `Dp(48)` = 48px，60px 图标居中后被 `clip.UniformRRect(box, box.Dx()/2)` 每侧裁掉 6px（12/60 = 20% 宽度）→ 被切掉的正是 logo 本体（图标自带品牌蓝底，非留白）。Dp 换算在别处都跟随 DPI，唯独这里写死。
  ② **羽化**：`fadeFrame` 的 `d0 := -inF + 1` 使实际渐隐跨度为 `fw − 0.5`，与本文件自身文档口径「核心（d ≤ -(fw+0.5)）= 1、边带渐隐到轮廓」**不符**。1× 下 `fw = clamp(round(Dp(48)×featherRatio), Dp(featherMinDp), Dp(featherMaxDp)) = clamp(round(1.44), 0, 3) = 1` → 跨度仅 0.5px；直边上带内唯一的像素中心恰在 d = −0.5 = d0 → t=0 → vis≡1 → **整条边全不透明**（复现测试修前红：轮廓内首像素 a=255）。高 DPI 下跨度尚存（fw=3 → 2.5px）故长期未被发现——D70 后果段记的「1×=1px 带宽」实为 0。
- **决策**：① **logo 随球径预缩放**：`logoImageOp(pxPx)` 按目标像素边长预缩放（`drawLogo` 取 `box` 短边），源图解码一次 + 按边长缓存单档，DPI/尺寸变化才重建（仍「预缩放 + 纯平移」，不做每帧仿射缩放）；`logoIconPx` 降为名义常量（只留注释与测试参考），不再参与绘制。② **渐隐跨度回归文档口径**：`d0 := -inF`（去掉 `+1`），跨度 = `fw + 0.5`——1× 下 1.5px、2× 下 3.5px，随 DPI 单调。
- **否决**：改 `featherRatio`/`featherMinDp` 把 1× 的 `fw` 抬到 2（D68 已把 ratio 0.03、上限 3dp 拍板为「收细」，重开调参属反复；且真因是跨度公式与文档不符，不是带宽取值本身）；只把固定 60px 改成按 125%→100% 的另一种写死换算（仍是写死像素，换 DPI 复现）；每帧对图标做仿射缩放（实证渲染不稳，且与既有「预缩放 + 纯平移」口径冲突）；把跨度定为 `fw`（丢掉 D47 的 `fw+0.5` 内缩标定，GDI 区块边界口径要重标）。
- **后果/限制**：① 边带确实变软：轮廓内首像素 1× 下 alpha≈66（原 255）、2× 下≈50（原 27）；已同步更新 `wantFeatherVis` 参考剖面与 `fade_test.go` 三处带测试的观测点——那三处原把形状边缘放在窗口边上、依赖旧的「边缘像素恒不透明」行为，现改为四周越界、观测落在核心。② **形状边缘像素现在确实会羽化**：此后凡「只考察带渐变/底带作用域」的观测类测试，必须让观测点避开边带（或让形状越出缓冲）。③ 图标缓存单档，DPI/尺寸切换时重建一次（`scaleBox` 纯 Go 面积平均）；球径取自 `box` 短边，非方矩形也不会越界。
- **状态**：生效

### D84 — 输入行带心跳：修展开态直采门控哑窗（§15.1，S1-1g 验收发现）

- **后果/限制**：① 透明条内「光标未在按钮矩形上」时 tooltip 不显示仍是**正确行为**——本项只消灭失聪、不放宽门控；光标自条内进入按钮矩形 ≤50ms 内点亮。② 自窗外直接落入条内仍无帧（无帧则无复评点）——继续移动必踩不透明像素自愈，且条内静置本就无 tooltip 需求。③ 带内静置常驻 20fps 仅发生在光标贴近输入行的交互时段，离开带（每 50ms 复评一次光标）即回零帧。
- **状态**：生效

### D91 — 跨块拖选 = 转写区观察者抢先 grab + `Regions` 几何自绘高亮（S1c，§15.3）

- **动机/实测**：用户提出「消息内容跨行选择」。现状：**块内**跨行拖选原生可用（D66 逐块 `Selectable`），但**跨块**（同一消息的多个段落块、跨消息）拖选不成立——D66 后果③「跨块拖选高亮分段，与拆行期等价」与实际不符（本决策更正之）。机制实证（Gio v0.10.2 源码）：① 按下时 handler 集合冻结（`io/input/pointer.go` Press 期定格 `p.handlers`，拖拽不再吸纳新 handler）；② 超 3dp slop 后 `gesture.Drag` 发 `pointer.GrabCmd`，grab 把其余 handler 全部 Cancel 并丢出集合（先到先得，`router.execute` 同步执行）——起始块的 dragger 因此永远收不到跨块事件，caret 钳在本块内。D63 否决过的 `posInRow`（按下过滤）与这堵 grab 墙是同一机制的两面。
- **决策**：范围 = **整个转写区跨消息连续**；复制 = **Ctrl+C**（拼接选中文本）。四件套：
  ① **观察者抢先 grab（方案 B）**：raw filter（D72 `logoRight` 同款，Kinds = Press|Drag|Release|Cancel），热区 `event.Op` **注册于转写视口 clip 内（与 `transcriptScroll` 同组）**——根级（layout 栈外）注册在行内容渲染后会被行组命中链跳组、Press 永远到不了观察者（实测缺陷；空态与根级可达只是巧合），同组注册与滚动手势同一命中链保证可达；在 `layout` 消费者阶段（measure 循环之前）pull——Press 命中可选块矩形记 candidate，Drag 超 3dp slop（`gtx.Dp(3)`，随 D90 缩放）即执行 `pointer.GrabCmd{Tag: 观察者}`：同步先到先得 → 块内 dragger 收 Cancel 退出，观察者保持 Drag/Release 直至抬手（Windows 驱动 `WM_POINTERDOWN → SetCapture`，窗外 Release 照常送达，无需按钮轮询/心跳兜底）。单击/双击选词/三击选行/shift+点击都发生在 Press 阶段、无 slop → 不触发 grab，原生行为无损保留。
  ② **锚/焦点模型**：grab 瞬间锚 = 起始块 `Selectable.Selection().start`（Press 已置 caret；双击选词后拖拽 → 锚自动为词首）；焦点 = Drag 事件 Position 经 `pointToCaret`（块 rect 命中 → 视觉行定位 → 行内 `Regions(mid,mid+1)` 二分）；块外夹取最近行缘；chip 头/分叉条无选键、不贡献文本。逐块 `[lo,hi]`：同块取区间、锚与焦点之间全选。几何底座 = measure 期对每块调 `Regions(0,n,nil)` 取每视觉行矩形（同帧 Layout 后有效、widget 相对）+ `rowStyle` 可选块组手工纵排取块内偏移 + 行原点 → 窗口坐标，按线性 selBase 键持久于 `keyRects`（帧末覆写、消费者阶段读上一帧，一帧陈旧可接受）。

- **否决**：方案 A（观察者不 grab、块内保留原生、Cancel 后轮询 `GetAsyncKeyState`+心跳收尾——任何文本拖拽都会收到 Cancel，同样要接管，却多出按钮轮询、心跳扩面与跨平台 stub，锚/焦点两头管理更脆）；逐块 Selectable 各自 `SetCaret` 拼高亮（widget 仅 focused 时自绘，多块同时聚焦不可行，焦点本是单 tag）；richtext/span 级选择（D65 已否，留后续，届时本机制的行几何直接复用）；OS 级 mouse hook/子类化（绕开 Gio 事件路由，破坏 headless 可测性）；v1 做 shift+点击跨块扩展与拖拽贴边自动滚动（增量留后续，滚轮在拖选中照常可用已覆盖基本需求）；TUI/REPL 同步实现（GUI only，同 S2b-Q15 口径）。

  ① **手势与命中**：`bubbleRight` 照 D72 `logoRight`（Secondary 按下武装、同指针原位抬起 fire，自挂 `pointer.Filter`——gesture 系跳过非主键，与 D63/D91 主键选态零冲突）；热区注册于转写视口 clip 内（与 D91 观察者同组命中链，D91 ① 实证根级注册不可达）。命中按**气泡底板矩形**：`paintRow` 期逐行登记 `bubbleRects{rect, bi, id, kind, keyBase, keyN}`（与 `u.record` 同一 bgRect）——padding 区也是气泡的一部分，且行选键矩形无块身份。
  ② **菜单项按块角色**：user 气泡 = 编辑/重新生成/复制；assistant 气泡 = 重新生成/复制（编辑不适用于生成文本）；thinking/chip/notice/live 草稿不响应（roadmap「可增：引用/查看原始块」不做）。上下文 `bubbleMenuCtx{id, kind, edit, copy}` 在 Gio 线程命中时组好，`atomic.Pointer` 过线程到 shell。
  ③ **呈现与分发**：`bubbleMenuMsg`（wmApp+4）投 shell 线程 → `showBubbleMenu`（光标位 `TrackPopupMenu`，TPM_RETURNCMD）→ 按项分发：重新生成 = `inputMsg "/regen <id>"`（与键入同路径）；编辑 = `editMsg` 回 Gio 进编辑态；复制 = `copyMsg` → 主循环记 `pendingCopy` → 下一帧 `gtx.Execute(clipboard.WriteCmd)`（剪贴板写入必须在 Gio 帧）。
  ④ **`/regen <id>`**：resolveNode → 沿 Parent 回溯找上游最近 user 消息（到 Root 未遇 user 报错）→ `Revise(userID, 原 Parts 整体拷贝, Fresh)`（保多模态）→ persist → **清屏回放** → `runTurn`。旧回答保留为历史分支（分叉条可见）。
  ⑤ **`/edit` 补回放**：Revise 移 Head 后清屏 + 回放——D81「转写区恒与 Head 一致」口径统一（/goto 同款；此前 /edit 只入树不回放是缺口，TUI 同样受益）。
  ⑥ **编辑流**：菜单编辑 → `editMsg` 预填输入框 + `editTarget` 态 + 轻提示（Enter 提交 / Esc 取消）；提交 = 结构化 `Command{Name:"edit", Args:[id, 文本]}`（**不经斜杠解析**——`parseEditArgs` 的 `Join(rest[1:], " ")` 对单元素是恒等，多行文本保真直达）；空文本视为取消；不回显 blockUser（修订结果由回放呈现）。
  ⑦ **复制口径**：有选区 → 复制选区（D91 选态直接复用）；无选区 → 整条气泡**渲染文本**（逐键 `Text()` 以 `\n` 拼接，与 `selCopy` 同口径）。
- **否决**：Gio 自绘菜单浮层（主窗无先例、ULW 位图命中语义添乱、TPM 管线现成且模态收尾由 OS 完成）；按行选键 `keyRects` 命中（矩形是文本行盒不含 padding，且无块身份）；/regen 用文本拼装 `/edit`（typed 解析多行必碎）；编辑弹独立小窗（输入框就地预填最轻）；Carry 重生成（旧回答子树会跟着新节点走，违背「旧回答保留为分支」）；复制原始 markdown（与 D91 渲染文本口径不一致）。
- **后果/限制**：① 「编辑文本恰以 `--keep` 开头」继承 typed 路径歧义（`args[1]=="--keep"` 识别为 Carry），不另立机制；② 编辑框单行：多行历史文本预填后以编辑框所见为准（所见即所发）；③ 编辑历史中段消息 = Fresh 分叉，其后旧消息转入旧分支（分叉条可切回），转写如实呈现；④ `/edit` 行为变化对 TUI 可见（清屏回放）；⑤ 收起态/动画期不响应（无转写区 / D54 口径）；⑥ 菜单文案为用户界面中文（语言约定）。
- **状态**：生效

### D93 — 编辑即重发 + `/regen` 无回答不重复分叉（S2 验收修正，§15.9）

- **动机（用户验收实测）**：S2 手工验收两缺陷，实为同一条链：① 右键编辑用户消息提交后只入树回放、**不重新生成**——Head 悬在无回答的新节点上，转写以"半截对话"收尾；② 用户接着点「重新生成」想拿到回答，`/regen` 无条件 Revise 上游用户消息 → 给**同文本**消息再造一个冗余兄弟分支（编辑节点依旧无回答），表现为"点击重新生成触发新分支（而不是生成回答）"。
- **决策**：① **编辑用户消息（Fresh）= 改写并重新生成**：`/edit` 在 Revise+persist+清屏回放之后，若修订节点为 user 且 Fresh → 直接 `runTurn`（Carry 是原地改写历史、Head 随转移子树，不重发；assistant/system 修订不触发生成）。② **`/regen` 分叉前置条件**：上游用户消息**尚无任何回答**（无孩子）→ 不 Revise——Head 不在其上则 Checkout（落盘），直接清屏回放 + 生成；已有回答才分叉重发（§5-Q3 口径不变，旧回答保留为分支）。
- **否决**：编辑后等用户手动重发（无回答的 Head 不是合法停驻态，转写呈现半截对话）；regen 一律直接生成不保留旧回答（违背 Q3「旧回答保留为历史分支」）；**回答级分叉**（Revise 助手节点成空壳再填充——与 agent「Head 之下追加」的 Turn 形状冲突，空 assistant 节点还需特殊渲染，成本与语义收益不成比例；用户消息级分叉语义自洽：旧问答整段成历史分支，分叉条 2/2 可整段切回）。
- **后果/限制**：① `/edit` 用户消息修订即产生一轮 LLM 调用（行为变化，TUI 帮助与 usage 文档同步）；② regen 无回答路径在 Head 已就位时无树变更、跳过 persist；③ 已有回答的 regen 仍在**用户消息**上出现版本分叉（2/2）——若期望「回答级」版本切换（分支条挂回答气泡下、用户消息不复制）属另一语义改动，见 D93 否决第 3 条，待用户明示再议。
- **状态**：生效

### D94 — 分支切换落到版本末端 `Tail`（S2 验收修正之二，§7.5/§15.3）

- **动机（用户验收实测）**：分叉条切换用户消息版本后**回答不显示**——D81 分叉条投递 `/goto <兄弟节点>`，而 `/goto` 把 Head 停在该消息节点上；其回答在子树里、不在 Head 路径上，清屏回放只剩半截。D93 让用户消息级分叉成为常态（每次编辑/重生成即一个新版本），该缺口从边角变成主流程。
- **决策**：① **domain `Conversation.Tail(id)`**：版本末端 = id 版本子树中 `CreatedAt` 最新的叶子（平局取 ID 序最大，保证确定性）；id 自身是叶子时即 id；id 不在树中 → ok=false。② **`port.TreeView` 增 `Tail`**：app 侧快照同次发布（post-order 聚合，O(n)），只读数据面扩展（S3 树 UI 可复用）。③ **分叉条切换 = `/goto <Tail(兄弟)>`**（GUI 侧经只读端口解析；端口不可用回退兄弟 id）；`/goto` 本身语义不动——停驻节点 = 新起点（§7.3 文档与 golden 口径不变）。
- **否决**：改 `/goto` 对非叶子目标自动延伸到叶子（破坏「设为新起点」的停驻用途——从中间节点续问/分叉是合法导航，golden 需重写）；GUI 直连 Session 算末端（铁律 5：树读取走只读端口）；新增 `/version` 命令（命令面膨胀——Tail 是导航辅助，非用户概念）。
- **后果/限制**：① TUI 手动 `/goto <用户消息版本>` 仍停在消息节点（文档口径不变；要完整版本可 /goto 其回答 id，`/branch` 可查）；② 版本末端取「最新叶子」——版本内更深分叉后，切回恢复到最近活跃末端；精确停驻任意中间节点仍可 `/goto`；③ Head 落在叶子（回答节点）上：继续输入即在该回答后续接，与对话常理一致。
- **状态**：生效

### D95 — 工具调用内嵌为 assistant 分片：Tool as Part（领域重构，§4.1/§7.1/§8）

- **动机**：tool 独立节点是全树最重的机制债——五处连锁复杂度皆由"调用与结果跨节点配对"而来：不变量 2（存在性引用）与 CallID 全树唯一检查、`hasCallID` 及其 skip 参数、`ErrReviseTool`、Prune 的失联 tool 收敛与改挂（约 30 行）、以及未来深拷贝子树时需递归重映射 CallID。Aquarius 的一次工具循环本就多次落库（assistant → tool → 下一步 assistant），工具执行发生在 turn 内，结果完全可以落进声明它的那个节点——跨节点引用彻底消失后，Prune 退化为纯粹的"删子树 + 光标回退"。
- **决策**：
  ① **形态**：Role 收敛四种（root/user/assistant/system），`RoleTool` 删除；`PartKind` 新增 `PartTool`，`ToolPart{CallID, Name, Args(json.RawMessage), Result(*tool.Result), Approval(ApprovalState)}` **同片承载调用与结果**（Result=nil = 未执行/被取消，正常路径由提交时点保证不出现）；`Message` 删 `ToolCalls`/`ToolResult` 两字段。`ApprovalState`（""/pending/approved/denied）为 M5 工具确认**预留字段**，本次不接线。CallID 降级为**节点内唯一**（checkNodeShape 把关）；PartTool 仅 assistant 可携带（与 D42 thinking 同规则）。
  ② **提交时点（D3 口径重述，Turn 粒度）**：**一次 Turn（可含多轮"生成+工具执行"循环）只提交一个 assistant 节点**——多轮的思考/正文/工具分片按到达序交错累积（`[thinking①, text1, tool{c1,r1}…, thinking②, text2, …]`），Turn 收场（正常/取消/失败/MaxTurns 用尽）时一次性 AppendCommitted，用户消息 : 助手节点 = **1:1**。先执行后提交，节点不可变不破；取消/装配级故障向未完成分片填 `OK=false` 结果（原 abortToolCalls 语义），树恒可装配。第 2 轮起构造请求把**未提交缓冲**投影为合成消息追加在 Path 之后（模型能看到前几轮的调用与结果；context_compact/autoCompact 的 mid-turn 摘要提交照旧，Turn 节点挂到最新 Head 之下）。
  ③ **port 投影口径**：`port.PromptMessage{Role:"tool", CallID}` **保留**——"tool 角色"降级为 API 投影概念（OpenAI 协议要求 assistant(tool_calls)→tool 应答交错），树上无此节点；装配把 assistant 节点**按工具分片边界切段**：每段产出 1 条 assistant 消息（Reasoning=段内思考拼接、Content=段内正文、ToolCalls=段内调用）+ N 条 tool 应答消息，`Result==nil` 的调用不声明也不应答；失联降级路径（`historyToolMarker`/declared 集合）整体删除——call 与 result 同片，结构上不可能失联。openai 适配器与 est 裁剪（port 层消息口径）零改动。
  ④ **事件序**：`Delta… → ToolCallEvent×N → ToolResultEvent×N →（下一轮 Delta…）→ … → CommittedEvent（每 Turn 一次）`；uitui/uigui 在**工具边界把流式草稿落为正文块**（重构前观感：正文气泡先于工具行/chip，第 2 轮文本重新流式），提交（每 Turn 一次）时就地回填权威文本并盖章——实时与回放块序一致；repl 实时天然兼容（文本已直写）。
  ⑤ **不变量**：不变量 2（存在性引用）删除（取代 D12），不变量剩两条（树合法、节点不可变）；`ErrReviseTool`/`hasCallID`/Prune 失联收敛全部删除（D18 取消——其存在前提是 tool 独立节点）；/rm 计数恰为子树节点数。
  ⑥ **磁盘破坏切换（D19 先例）**：旧格式（role:"tool" 节点或节点带 `tool_calls`/`tool_result` 字段）Load/List 显式报 `ErrLegacyFormat` 点名 ID，**不自动迁移**；检测走影子结构（内嵌领域结构 + 遗留字段）——普通 Unmarshal 会把 assistant 的 `tool_calls` 静默丢弃，残留 tool 角色节点的文件才会失败，纯 tool_calls 文件会"看起来正常"地丢数据，必须显式识别。
- **否决**：结果回填时就地改写已提交节点（破不变量 3/D1）；保留独立 tool 节点（本次要除的债）；每工具轮一个节点（D95 初版口径，被本条 Turn 粒度取代——一次带工具的对话会产出多个 assistant 节点，违背"用户:助手 1:1"的对话直觉，且 UI 需把一轮对话拆显示）；port.PromptMessage 改为携带 tool 分片（把 API 消息拆分推进适配器，投影边界劣化）；Load 时自动迁移（个人助手虽有真实数据，但迁移正确性风险与两套格式长期共存成本不值——破坏切换 + 原地旧文件手工处置，.bak 兜底不变）。
- **后果/限制**：① ~/.aquarius 既有含工具调用的会话升级后不可读（List 点名 ID），需手工删除或留存备份；② 事件序与提交粒度变化对三 UI 内部实现可见（golden 既有脚本无工具场景，不受影响）；③ 纯工具轮（无正文）仍是合法节点形态（D89 锚点口径不变）；④ 执行中崩溃 → 该 Turn 整节点未提交（文本随失，树仍合法）——较旧形态（calls 已提交、结果缺失致下次装配 400 隐患）更稳；⑤ **分叉条每 Turn 一个挂点**（末个正文气泡，纯工具轮在 chip——D81/D89 口径随粒度调整）；⑥ `/edit` 命中多段 Turn 节点时**整节点内容替换**为编辑文本（旧版本整段留分支）；⑦ 通知/TTS 扇出（D28）每 Turn 一次——中间纯工具轮不再触发 Deliver；⑧ 一节点可含多段 PartThinking（每轮生成一段，D42"至多一段"限定从"流内"放宽为"每轮"）；⑨ Turn 中途切换模型（/model 热切换）不可达（命令在 Turn 间串行），节点 Model 取收场时的当前模型。
- **状态**：生效

### D96 — Revise 第三模式 `Clone`：深拷贝子树分叉（§4.1）

- **动机**：Fresh 丢后续历史；Carry 的子树身份与旧版本绑定（原子树只属于旧分支，无法两份独立演进）。需要"复制整段历史试另一种走向、两份互不影响"的分叉形态（如复制一段含工具执行的对话做对照重放）。D2 当年否决"深拷贝子树"针对的是**以拷贝替代 Carry**（数据翻倍 + 身份分裂成为默认行为）；本决策将其立为与 Fresh/Carry **并列的显式第三模式**，按需选用。
- **决策**：`KeepMode` 新增 `Clone`：新节点（同父同角色、内容替换）+ 以旧节点为根的**整棵子树深拷贝**挂其下——拷贝节点 ID 全新、与原子树零对象共享（内容经 Clone 深拷），旧节点及其子树字节级不动；`RevisedFrom[新根] → 旧根` 仅记一条；拷贝节点保留原 `CreatedAt`（保真历史时刻，Tail/Branches 排序仍成立，确定性由 ID 唯一性保证）。Head 语义：旧 Head 若在原子树内则**平移到拷贝对应节点**，否则移到新节点。仅入领域 API 与性质测试，不接命令（等真实用例再设计命令面）。
- **否决**：拷贝节点沿用旧 ID（身份冲突）；拷贝时重映射工具 CallID（D95 后 CallID 仅节点内唯一，无跨节点配对，天然无需重映射——正是 D95 的预期收益之一）；RevisedFrom 逐节点记录拷贝链（版本链语义是"修订"，整树拷贝只在新根记一条）。
- **后果/限制**：① 数据翻倍是该模式的固有代价，仅显式选用时发生；② 命令面/右键菜单暂无入口（`Fresh`/`Carry` 仍服务于 /edit /regen 现有语义）；③ 拷贝出的子树与原子树在 Branches 里同属旧节点的"同级分叉"视角之外（挂在**新节点**之下），树 UI 呈现时以 RevisedFrom 版本链为准。
- **状态**：生效

### D97 — 分叉三方式编辑：Fresh/Carry/Clone 命令面与右键菜单（S2 增强项，§4.1/§7.3/§15.9）

- **动机（用户需求，2026-10-05）**：D96 将 Clone 入域层时明言"等真实用例再设计命令面"——真实用例即修订消息时对「后续历史去向」的三选一：**编辑**（新分叉，旧问答留旧分支）/ **编辑并转移历史**（后续历史随修订走，旧版本只剩该消息）/ **编辑并复制历史**（两份独立演进）。同批拍板：**助手消息也开放编辑**（解除 D92 ②「编辑不适用于生成文本」），且助手修订**一律不自动续生成**。
- **决策**：
  ① **命令面**：`/edit <id> [--keep|--copy] <文本>`——`--keep`=Carry（既有），新增 **`--copy`=Clone**；flag 须紧跟 id（parseEditArgs 位置口径不变，flag 置于 id 前仍报用法错误）。GUI 编辑态结构化提交复用同一 token 序列：`Args=[id, ("--keep"|"--copy")?, 文本]`——单一解析路径，typed/结构化两端共享（`port.Command` 形状不动）。

- **动机**：roadmap S1c「后续增量」——拖选跨出视口时选区无法继续扩大（指针停在视口边缘，落点不再前进；滚轮可滚视图但焦点端点不随动）；编辑器惯例 = 拖到视口边缘自动滚动且选区端点随动。

- **状态**：生效

### D106 — 展开按钮实装：胶囊原地增高多行编辑（S2b-4，§15.2）

- **动机**：roadmap S2b-4——D49 展开灰槽（四角括号、不可点）实装；§15.2 既有口径「输入栏变大（多行长文本编辑），可再收起」「Enter / Shift+Enter 发送 / 换行（展开态多行编辑同规则）」。形态用户拍板（2026-10-05）：**胶囊原地增高**。

### D106 修订 — 展开态验收反馈四项（2026-10-06，S2b-4）

- **动机**：D106 首版手工验收实测四项缺陷/体验问题（附截图）：光标多行伸长、内容居中、槽位位置、收起丢换行。
- **决策**：
  ⑴ **光标高度按单行**：fade pass 自绘 caret（D62）原按编辑器内容高 0.8/0.2 拆分——多行时正比于行数伸长（实测缺陷：单行正常、三行伸长三倍）。改为按**同字号单行量测高**取行高，基线仍取 CaretCoords().Y（多行下随行走）。
  ⑵ **展开态排版**：多行编辑区**顶对齐**（原 Flex Middle 居中——首行悬在半空）；附件槽/展开槽移至胶囊**顶角**（附件左上、展开右上，构成工具行，编辑区占余高）——composer 惯例。常态单行布局不变。
  ⑶ **收起保留换行**（推翻决策③「收起压平」）：收起/收起窗口一律**不改文本**——SingleLine 切换不触 buffer、已有 `\n` 原样保留；单行胶囊内多行显示溢出裁剪可接受，**数据保真优先**（提交恒发真实文本，重新展开即完整多行）。
  ⑷ **编辑多行消息自动展开**：editMsg 应用时文本含 `\n` 即**先展开再预填**（SingleLine=false 下 SetText 保真）——顺带修复原「预填即压平」的隐藏缺陷（编辑多行消息时换行在进入编辑态就丢了）。
- **状态**：生效

- **修订⑸（2026-10-06 二轮验收）**：① 工具行加**顶边距 10dp**（原贴胶囊顶缘、与 24dp 圆角曲线相切显挤）；② 展开高度 120dp → **160dp**（≈6 行，用户反馈再加高）。
